# Plan: Define Data Formats Precisely

Status: done
Date: 2026-08-25
Related backlog item: `.plan/000-backlog.md` — "Define data formats precisely: notes (Markdown `.md`), tasks (workspace format TBD), folders (real directories), StartSpace metadata linked to Bookmark IDs (JSON shape TBD), config (JSON shape TBD)."
Related ADR: `docs/decisions/0002-manifest-permissions-storage.md` — record final shapes here.

## Goal

Define, precisely, the data formats StartSpace uses so implementation can proceed without ambiguity:

- Notes (Markdown `.md`)
- Tasks (workspace format)
- Folders (real directories)
- StartSpace metadata linked to Bookmark IDs (JSON shape)
- Config (JSON shape)

And resolve the open questions listed in ADR 0002.

## Decisions

### 1. Notes — Markdown (`.md`)

Notes are real Markdown files in the workspace. No proprietary format. A note is a `.md` file whose filename is the note's identity within the workspace.

Convention (to be enforced by the UI and documented; not a browser requirement):

- Filename: the user-chosen name with `.md` extension. Normalize to a filesystem-safe form on create/rename (e.g., disallow path separators and trailing dots; collapse leading/trailing spaces). The extension does not rename arbitrarily — it follows the user's intent and only sanitizes where the filesystem requires it.
- Content: any valid Markdown. Rendering in the UI uses `marked`.
- Metadata inside the note: none required by StartSpace. StartSpace does not impose a required frontmatter schema on notes — notes remain plain Markdown usable in VS Code, Obsidian, etc. If StartSpace needs per-note metadata (e.g., for linking or display), it derives it from the filename and content, or stores it in StartSpace metadata keyed by note identity, not by mutating the note file. (Keep this rule explicit: do not turn notes into a StartSpace-specific format.)

### 2. Tasks — workspace `tasks.json`

Tasks are stored in the workspace as a single JSON index file: `tasks.json` at the workspace root.

Why a JSON index rather than individual task files:

- A Kanban board is naturally an ordered collection with status, ordering, and links. A JSON index is the simplest representation that supports CRUD, reordering, status changes, and linking to notes/bookmarks without imposing a file-per-task structure on the user's folder.
- It stays local, portable, and JSON-consistent with the rest of the stack.

Format (initial version):

```json
{
  "version": 1,
  "tasks": [
    {
      "id": "task-<unique-id>",
      "title": "Learn Proxmox",
      "status": "todo",
      "column": "backlog",
      "order": 0,
      "noteIds": [],
      "bookmarkIds": [],
      "created": "2026-08-25T10:00:00.000Z",
      "updated": "2026-08-25T10:00:00.000Z"
    }
  ]
}
```

Fields:

- `id` — stable unique identifier for the task. Generated by StartSpace; not a browser or file-system ID.
- `title` — task title text (user-editable).
- `status` — free-form status string. Initial Kanban columns are a UI/ordering concern; `status` carries the column/state value.
- `column` — the Kanban column the task currently lives in (e.g., "backlog", "in-progress", "done"). Define the initial column set during implementation; keep it as data so it can evolve.
- `order` — ordering within a column.
- `noteIds` — list of note identities StartSpace knows about that are linked to this task. (How note identity is represented is defined below — see "Note identity for linking.")
- `bookmarkIds` — list of browser Bookmark IDs linked to this task.
- `created`, `updated` — timestamps.

Task identity for linking: a task is identified by its `id`. Linking a note to a task means recording the note's identity in the task's `noteIds`. Linking a bookmark means recording the browser Bookmark ID in the task's `bookmarkIds`.

### 3. Folders — real directories

No change. Folders are real directories in the workspace, created via the File System Access API from the Notes page UI. They hold Markdown notes and can be nested. Visible to external tools. No StartSpace metadata file is required for a folder.

### 4. Note identity for linking

A note's identity for linking to tasks is its path relative to the workspace root (e.g., `notes/welcome.md`), normalized as a stable string. This is stable as long as the note is not moved/renamed; if it is moved or renamed, StartSpace updates any links that reference it (implementation detail — decide the rename/move behavior during implementation, see open questions).

Alternatives considered for note identity:

- File name only: collisions across folders make this ambiguous.
- Full path relative to workspace root: disambiguated, portable across moves within the workspace if the path is updated, and does not require a separate ID scheme. Adopted.

### 5. StartSpace metadata linked to Bookmark IDs — JSON shape

Stored in extension storage. Keyed by browser Bookmark ID. This is StartSpace's link to the browser's bookmark store (the browser is the source of truth for the bookmark itself).

Initial shape:

```json
{
  "bookmarkMetadata": {
    "<bookmarkId>": {
      "favorites": true,
      "tags": ["programming", "proxmox"],
      "dateAdded": "2026-08-25T10:00:00.000Z",
      "relatedNotes": ["notes/welcome.md"],
      "relatedTasks": ["task-<unique-id>"]
    }
  }
}
```

Fields:

- `favorites` — whether the bookmark is a favorite (displayed on the homepage). Boolean.
- `tags` — user-assigned tags. Array of strings.
- `dateAdded` — when StartSpace first saw/linked this bookmark.
- `relatedNotes` — note identities (relative paths) linked to this bookmark.
- `relatedTasks` — task IDs linked to this bookmark.

### 6. Config — JSON shape

Stored in extension storage. Extension-owned, small, serializable.

Initial shape:

```json
{
  "version": 1,
  "webSearchEngine": {
    "name": "Google",
    "urlTemplate": "https://www.google.com/search?q={query}"
  },
  "currentWorkspace": {
    "id": "<workspace-id>",
    "name": "My Workspace"
  }
}
```

Fields:

- `version` — config schema version for forward-compatible reads.
- `webSearchEngine.name` — human-readable name shown in Settings.
- `webSearchEngine.urlTemplate` — URL template with a `{query}` placeholder. The search bar substitutes the query into `{query}` and opens the resulting URL (see web search host permission decision below).
- `currentWorkspace.id` — a StartSpace-generated workspace identity, used to recognize the same workspace across sessions. Not the filesystem path (paths can change; the identity is stable for the granted handle).
- `currentWorkspace.name` — user-visible workspace name.

Scope of config for v1: web search engine and current workspace identity. Do not preload settings that are not yet in the product (no theme, no keyboard shortcuts, no command palette config). Add fields only when the feature exists.

### 7. Workspace-scoped metadata files in the workspace — decision for v1

For the initial version, the workspace contains: notes (`.md`), `tasks.json`, and folders. **No extra workspace-scoped JSON metadata files are required in v1.**

If StartSpace later needs a workspace-level index (e.g., a search index, a note index, a manifest of known note identities), it can add one — but only when there is a real need, not preemptively. This keeps the workspace minimal and maximally compatible with external tools.

## Open questions resolved

### Q1: Exact manifest keys for the New Tab override in each target browser

- Chromium: `chrome_url_overrides` with the `newtab` key. Confirmed standard.
- Firefox: also supports `chrome_url_overrides` in WebExtensions. Confirm during implementation that the target Firefox version honors it for the New Tab override, and record the result in the manifest/permissions ADR or a follow-up ADR.
- Decision: use `chrome_url_overrides.newtab` as the primary mechanism; Chromium first. Firefox support to be verified during implementation rather than assumed.

### Q2: Does the File System Access API require a manifest permission?

- Chromium: the File System Access API is available to extension pages/scripts but is gated by the user via `showDirectoryPicker()` — a user gesture. It is not a manifest permission in the sense of `permissions` declaring blanket access. The user grants a specific folder at runtime.
- Firefox: the File System Access API has limited/experimental support. If Firefox is a target, this is a constraint to handle explicitly (e.g., the workspace flow may not work the same way, or at all, in Firefox until support matures).
- Decision: do not declare `fileSystemAccess` as a blanket manifest permission unless implementation confirms a browser requires it. Treat workspace access as runtime-gated via `showDirectoryPicker()`. Document the Firefox limitation as an open implementation concern rather than pretending it is resolved.

### Q3: Does the web search fallback need a host permission?

- The search bar constructs a URL from the user-configured `urlTemplate` with the query substituted into `{query}` and opens it (e.g., in a new tab). This does not require fetching search results through the extension — the browser navigates to the search engine. No host permission is required for this in the initial version.
- Decision: `host_permissions: []` for v1. If a future version fetches results inline or does anything that requires host access, re-evaluate and declare the smallest necessary pattern.

### Q4: Exact JSON shapes for config and StartSpace metadata (favorites, tags, date added, related notes/tasks by Bookmark ID)

Defined above in sections 5 and 6. Record the shapes in the ADR. Keep them versioned (`version` field) so future reads can be forward-compatible.

### Q5: Task storage format in the workspace

Decided: a single workspace JSON index file `tasks.json` at the workspace root (section 2). Not individual task files, not Markdown task files, not a database. JSON index supports the Kanban model and stays local/portable.

### Q6: Whether any workspace-scoped metadata is needed at all in v1

Decided: no extra workspace-scoped JSON metadata files in v1 beyond `tasks.json`. Notes are `.md` files; folders are directories; `tasks.json` is the task index. If a workspace-level index is needed later, add it when there is a real need (section 7).

## Validation

- The JSON shapes are stable enough that a later implementation pass can build serialization/deserialization against them without redefining them.
- The decisions do not introduce a backend, a cloud dependency, or a proprietary note format.
- Notes remain plain Markdown usable outside StartSpace.
- The workspace stays minimal for v1 (notes + tasks.json + folders).

## Risks

- Firefox File System Access API support is an implementation risk, not resolved here. Kept as an explicit open implementation concern.
- Rename/move of notes changes the relative path used as note identity; linking consistency on rename/move is an implementation detail to decide during implementation (not blocking this plan, but must not be forgotten).
